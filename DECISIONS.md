# Architecture Decisions

Short records of the decisions behind Choppy. Newest decisions go at the bottom. If a decision changes, mark the old one *Superseded* and add a new one.

---

## ADR-001 – App structure: SwiftUI feature modules + `ChoppyCore` package
**Status:** Accepted (2026-10-30)

- The app target `choppy` holds the UI and Apple frameworks: SwiftUI, SwiftData, CloudKit, GameKit, Speech, Translation, FoundationModels.
- Each feature lives in `choppy/Features/<Feature>/`. Every screen has an `@Observable` view model ("MVVM-light").
- Services sit behind protocols (`SpeechService`, `ChatTutorService`, `TranslationService`, `PairSyncService`, `ContentProvider`, …) and are injected through `AppEnvironment` in the SwiftUI environment, so previews and tests can use mocks.
- Pure domain logic lives in the local Swift package **`Packages/ChoppyCore`**: SRS, kana/romaji, content model and parsing, game rules and scoring, weekly plan logic. It has no UIKit, SwiftUI or CloudKit, so `swift test` runs in seconds on the Mac without a simulator.

**Why:** game rules, SRS and Shiritori need many fast unit tests. A separate package keeps them honest about dependencies. Features stay in the app target because of SwiftUI previews and SwiftData macros.

## ADR-002 – Persistence: SwiftData (private) + CKSyncEngine (shared pair space)
**Status:** Accepted (2026-10-30)

- **Private data** (SRS cards, review log, settings, streak, XP) is stored in SwiftData with `cloudKitDatabase: .private("iCloud.chop.app.choppy")`, which syncs automatically.
- **Shared pair space** (weekly plan, goals, custom vocab, game, test and challenge results) is stored in a local-only SwiftData store and synced by **`CKSyncEngine`** into a custom zone `PairZone`. The zone is shared as a **zone-wide `CKShare`**: the owner syncs through the private DB, the partner through the shared DB.

**Why:** in iOS 26, SwiftData still cannot work with `CKShare` or the shared database. The alternative, `NSPersistentCloudKitContainer`, does support sharing. But it would add a second persistence stack (Core Data) with an opaque mirroring schema and implicit conflict behaviour. `CKSyncEngine` costs us record mappers for about 7 record types. In return we get explicit conflict rules and one local model layer.

**Conflict rules:** results are append-only records with UUIDs, so they never conflict. Plans, goals and custom vocab use last-writer-wins on `modifiedAt` / `modifiedBy`.

**Constraints:** SwiftData models that sync via CloudKit have only optional or defaulted properties, no `@Attribute(.unique)`, and only optional relationships.

## ADR-003 – Content: bundled, versioned JSON with stable IDs
**Status:** Accepted (2026-10-30)

- Content ships as `choppy/Resources/Content/choppy-content.json` (`formatVersion` for the file layout, `contentVersion` for the data), generated by `Tools/ContentPipeline` (a Swift CLI) from JMdict, KANJIDIC2, KanjiVG and Tatoeba plus hand-written topic lists. `ContentLibrary` (ChoppyCore) decodes it, validates it (unique IDs, known topics, German meanings present, furigana adds up to surface and reading, difficulty 1–5) and indexes it. Invalid content fails a unit test, and in debug builds an assertion at launch.
- **Kana are code, not JSON** (`KanaCatalog` in ChoppyCore): the table is fixed, and code lets the romaji input check reuse it later. Hiragana is written once; katakana is derived by the Unicode offset 0x60. 104 characters per script (46 basic, 25 with dakuten/handakuten, 33 yōon). Keys are Hepburn romaji except ぢ/づ (`di`/`du`), which would otherwise clash with じ/ず.
- Until the pipeline exists (Phase 1, step 4), a small hand-written greetings topic uses source `choppy` (`vocab:choppy:konnichiwa`). The pipeline may replace these IDs, since no user data references them yet.
- Every item has a stable `ContentID` (`kind:source:key`, e.g. `vocab:jmdict:1206730`, `kana:hiragana:ka`). SRS state and plans reference **only IDs**, so content updates never break schedules.
- Share-alike licenses (CC BY-SA) apply to the content bundle, not the app code. All sources are attributed on the Credits screen.

## ADR-004 – Spaced repetition: FSRS-6, own implementation
**Status:** Accepted (2026-10-30)

FSRS models recall better than SM-2 and needs fewer reviews for the same retention. The core is about 300 lines, so we implement it in `ChoppyCore` and test it against reference values from `py-fsrs`. That avoids a dependency for a central algorithm. Target retention is 0.9 with default parameters; per-user optimization from `ReviewLog` can come later.

## ADR-005 – Multiplayer transports per game type
**Status:** Accepted (2026-10-30)

| Game type | Transport |
|---|---|
| Real-time, timed | Game Center `GKMatch` (later optionally MultipeerConnectivity) |
| Turn-based | `GKTurnBasedMatch` |
| Async challenge | `AsyncChallenge` record in `PairZone` |
| Pass-and-play | local |

All games use the shared framework: `GameDefinition`, `GameSession`, `GameTransport`, `ResultRecorder`. Rounds are seeded so both players get identical items.

## ADR-006 – Speech: Kokoro bundled + pre-rendered audio, system voice fallback
**Status:** Accepted (2026-10-30)

- `SpeechService` has three implementations: `KokoroSpeechService` (Core ML, Apache-2.0, **bundled** in the app per your decision), `SystemSpeechService` (`AVSpeechSynthesizer`, ja-JP) and `CachedSpeechService`.
- Audio for bundled content is **pre-rendered** in the content pipeline with full-quality Kokoro (pyopenjtalk G2P) and bundled as AAC.
- On-device Kokoro is used only for user-added text, with kana→phoneme mapping and no pitch accent. A spike in Phase 2 decides whether it beats the system voice.

## ADR-007 – Chat tutor: Foundation Models, behind a protocol
**Status:** Accepted (2026-10-30)

Both of your devices support Apple Intelligence. `FoundationModelsTutor` checks `SystemLanguageModel.default.availability` and Japanese locale support at runtime, and shows a graceful fallback state if either is missing. A Japanese quality spike is planned in Phase 3.

## ADR-008 – UI language German, light mode only, Noto Sans JP
**Status:** Accepted (2026-10-30), font part superseded by ADR-010

- The development region is **German** (`de`). Strings live in a String Catalog (`Localizable.xcstrings`), so English can be added later.
- Light mode only: `UIUserInterfaceStyle = Light` plus `.preferredColorScheme(.light)`. All colours are semantic tokens, so dark mode only needs added variants.
- The accent font is **Noto Sans JP** (variable weight 100–900, OFL), registered via `UIAppFonts`. It contains kana and kanji, so it can be used for Japanese text as well. German body text uses SF.

## ADR-009 – No third-party dependencies (for now)
**Status:** Accepted (2026-10-30)

Every future dependency needs a written justification here before it is added.

## ADR-010 – Adjustable theme, Teko accent font, custom navigation, portrait iPhone
**Status:** Accepted (2026-10-31)

- **Colours live in code, not the asset catalog.** `ColorToken` holds the defaults; `ThemeStore` (`@Observable`, saved in `UserDefaults`) holds overrides set in the in-app editor "Farben & Stil" (Wir tab). `Color.paper` etc. read the store, so every view redraws when a colour changes. Generated asset symbols are switched off (`ASSETCATALOG_COMPILER_GENERATE_SWIFT_ASSET_SYMBOL_EXTENSIONS = NO`); `AccentColor` stays only as the system fallback tint. The editor can share the current values as text, so a look the users like can become the new defaults.
- **Colours come from the forest reference palette** (`ColorToken.referencePalette`), the two yellows made more golden: Pergament #F5E1B9, Sand #D8AF7F (paperDeep), Sonnengold #F3C24A (gold, was #F6D573), Honiggold #DEA537 (warning, was #E2B553), Ocker #BB8A44 (wood), Erde #80673B (inkSoft), Stein #8E7D69, Rinde #5A5034 (woodDark), Schatten #464232 (ink), Farn #909F43 (bamboo), Moos #5F6F3A (success), Tanne #495635 (accent). Exceptions: the background `paper` is #D5CE98, the green of the lower hill silhouettes (fern on parchment); `card` #FBF0D6 and `accentSoft` #DCD19C are light tints of palette colours (the palette has no near-white); `hanko` stays seal vermilion #B4412F. Maple leaves use stamp red (`leafRed` #B4412F) and two palette browns (`leafLight` ochre #BB8A44, `leafDark` earth #80673B). The editor offers the whole palette plus hill green and stamp red as suggestions for every colour. The store key is `theme.v4`, so overrides saved under older defaults are dropped.
- **Accent font is Noto Sans JP** (2026-11-04, after trying Teko). Teko (OFL, Latin only, `Teko-Light_<Weight>`, set 1.3× larger) stays bundled as an option in the editor. Japanese text always uses Noto Sans JP.
- **One background for all screens**, chosen in the editor: Schlicht, Momiji (default), Seigaiha, Asanoha, Kikkō, Shippō, plus pattern strength and paper grain. Every screen gets it through `ChoppyScreen`. Momiji uses deeply cut maple leaves in palette colours. `backgroundLayout` `.full` (most screens) is an even Poisson-disc scatter of single leaves (no rows, columns or clumps). `.framing` (Pfad) is painted in sumi-e style after an ink-and-watercolour maple reference: green misty hills, dry ink-brush branches with drooping twigs reaching in from both edges at irregular heights, and slender seven-lobed leaves hanging from thin stalks as translucent washes (pigment pooling in the middle, darker dried edges, fine veins), keeping the footprint path free. The pattern is laid out at full window size (including safe areas) from the top edge, so the copy behind the header lines up with the page. Because that copy is only clipped visually, `AppBackground` disables hit testing; without it the header background swallowed every tap on the page.
- **No system navigation bar or tab bar.** `ChoppyScreen` draws the header (vermilion seal with the Japanese name, title in the accent font, brush stroke) and hides the system bar; a `UINavigationController` extension keeps the swipe-back gesture working. `RootTabView` keeps all tabs alive in a `ZStack` and floats `BambooTabBar` over them – one flat bamboo stalk with fine ink outlines (no gradient, nothing behind it), one section per tab, two small leaf sprigs, and only the right end drawn cut open (as seen in perspective); the selected tab is only inked darker, no background fill; its height reaches screens as `bottomBarInset` and becomes a bottom content margin for scroll views, so the page background still runs underneath the bar.
- **iPhone only, portrait only** (`TARGETED_DEVICE_FAMILY = 1`). Both users have iPhones, and a portrait-only app on iPad would run letterboxed or need extra layouts.
